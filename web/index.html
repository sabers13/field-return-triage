Before taking this further

Public data, different setting
US vehicle complaints stand in for return reports. They do not contain a lab’s test history or represent one supplier’s parts.
Labels are imperfect
Component and safety fields come from a public coding process, not an engineer’s finding. Scores inherit that uncertainty.
Test suggestions are examples
A lab needs its own test catalogue, inspection points and escalation rules. A suggested test is not a confirmed diagnosis.
Agreement is not accuracy
Conditions such as moisture or vibration have no ground-truth labels here. Their score measures agreement with a fixed keyword rule.

This is a measured portfolio project. It has no production queue, authentication or validated deployment in a returns lab.

A traceable next step

Which returned parts need a closer look, and which test should run first? The flow keeps the original complaint attached to every suggestion.

  1. AI extraction

    Find the clues

    Read the complaint for symptoms, conditions and safety indications. Return a quote for each clue.

  2. Code

    Check the words

    Drop any clue whose quote does not appear in the original complaint.

  3. Hard rules

    Put safety first

    Safety goes to priority 1 with human review. Unclear cases go to human reading.

  4. Search + rulebook

    Suggest the test

    Find similar past cases. Map the checked clues to tests, inspections and questions.

  5. Technician

    Make the decision

    Accept the suggestion or change it with a reason. The real pipeline logs this feedback.
