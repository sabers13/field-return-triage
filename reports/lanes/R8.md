The page has the six sections the brief asks for:

1. **Headline and the three sentences.** The H1 is the PLAN §1 question; “It
   reads / It routes / It does not decide” is exactly three sentences, with the
   last one saying a technician accepts or changes every case. A rule card repeats
   the AI-suggests / code-checks / technician-decides split.
2. **Flow.** The PLAN §4 chain: complaint text → extract (model) → quote check →
   hard rules → similar cases → suggest next step → technician → feedback log,
   with the separate trend-watch path below. Actor colours distinguish model,
   code and person.
3. **Queue.** 12 cards, picked by the fixed rule below, with highlighted quotes,
   suggested test + reasons + what to ask for, the three nearest past cases, the
   model/prompt/rulebook/hard-rule/schema versions, and demo accept/change
   controls. The demo keeps its state in memory only: no storage call and no
   network call; even the reason select is thrown away on reset.
4. **Results.** A model scorecard (macro-F1, safety recall and precision, quote
   grounding, needs-human share, cost per 1,000, all with 95% CIs), the three
   cost-free baselines, and a source card per model naming the which-ai-model
   card path and pinned commit.
5. **Trend watch.** The example series bar chart (302 weeks) with the alert week,
   the recall and the 365-day window marked; the backtest statistics against the
   seeded base rate; the one-line honest reading.
6. **Limits.** US complaints as stand-ins, noisy coded labels, an example
   rulebook, and condition agreement is not accuracy.

### The queue rule

The primary model (`muse-spark-1.3-contributor`) produced all 400 replay cards;
the comparison model only ran the first 200 after the R7 budget cut. The page
uses the primary cards and takes four per priority, lowest numeric complaint id
first, with no sampling or hand-picking:

| Priority | Cards |
|---|---|
| 1 — safety first | `11633747`, `11634070`, `11634092`, `11635306` |
| 2 — clear clues | `11633614`, `11633796`, `11634690`, `11637476` |
| 3 — needs human reading | `11637975`, `11638530`, `11641193`, `11649169` |

`build_page_data` raises if a priority cannot supply four cards, so a partial
queue can never ship silently.

## Deviations and shared-file changes

1. **`Makefile`** — only the two R8 stubs (`page-data`, `page`) were replaced with
   the report CLI calls; every other target is unchanged. `docs/INTERFACES.md`
   §10.6 explicitly hands those stubs to this lane.
2. **`results/MANIFEST.sha256`** — `make page-data` rewrites the manifest after
   writing `results/page/page-data.json`, so the new results file is covered by
   the same manifest as every other results file. Without that, `make all` would
   leave a results file outside the documented replay check. No other results
   file changed.
3. **Screenshots are evidence, not page assets** — they live in the task folder
   (rule 2), not in `results/page/screenshots/`. R9's README (merged after this
   lane started) says they “live under `results/page/screenshots/` and are linked
   from the live page”; the brief for R8 says the task folder. The four files are
   available at the paths above if R9/R11 should copy them into that slot or
   reword the README. R8 did not link them from the page because a relative link
   from `dist/` would not survive publishing only the `dist/field-return-triage/`
   directory.
4. **Queue model** — the brief says “from the replayed eval set”; the page uses the
   primary model's 400 cards rather than mixing in the comparison model's 200,
   because the fixed 4/4/4 rule needs a complete set per priority and the
   primary is the card a technician would actually see.
